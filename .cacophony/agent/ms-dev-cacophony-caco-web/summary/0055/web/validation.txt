Validation evidence for bd-f9fd61:

- Before: 2 hot-path filter persistence functions
  (persistAgentFilters, persistBeadFilters) called
  localStorage.setItem synchronously on every keystroke.
  Each setItem is ~1-5ms of synchronous disk I/O. Typing
  a 7-char query meant 7 writes when only the LAST stored
  value matters for page reload.
- After: new persistToLocalStorage(key, value, delayMs = 250)
  helper coalesces writes per key via setTimeout debounce.
  Companion _flushPendingPersists synchronously drains any
  pending writes on visibilitychange -> 'hidden' (tab switch /
  minimize) and on pagehide (actual page unload, BFCache-
  friendly). So the user's last-typed state survives close/nav.

- Why setTimeout (not rAF like bd-3c01a1):
  - Render work needs rAF (one render per frame; humans can't
    see between frames).
  - Storage work needs setTimeout debounce (no UI waits on the
    write; we want to write only when user pauses typing). rAF
    would still fire ~60 writes/sec while typing fast.
  - 250ms sits comfortably below average human pause-between-
    keystrokes (~350ms) while well within visibilitychange budget.

- Preserved as immediate: updateHashForCurrentView() calls
  (the URL hash is the source of truth for shareable filter
  state; copy-paste mid-typing should reflect current input).
