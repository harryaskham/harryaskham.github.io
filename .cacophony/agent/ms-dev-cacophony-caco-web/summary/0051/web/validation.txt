Validation evidence for bd-3c01a1:

- Before: 7 search/filter inputs called full re-render functions
  (renderAgents, renderBeads, filterLogs, renderFeed, etc.)
  on every keystroke. For instances with hundreds of agents /
  beads / log entries, typing a 7-character query triggered 7
  full dataset iterations and 7 innerHTML rebuilds.
- After: each site wraps the expensive render in
  scheduleRender(fn), an rAF-coalesced helper. Rapid keystrokes
  now collapse to one render per repaint frame (~16ms at 60Hz).
  Persistence calls (persistAgentFilters, persistBeadFilters)
  preserved as immediate -- they're cheap and want to fire
  frequently.

- Why rAF over setTimeout debounce:
  - rAF runs at browser repaint cadence -- coalesced renders
    feel instant.
  - setTimeout(..., 150) introduces a real perceived delay.
  - rAF auto-pauses on hidden tabs.
  - Keyed by function identity via Map -- two different render
    fns don't cancel each other.

- Direct foreground validation (per revival nudge; not queued/backgrounded):
    cargo test -p caco-web --lib search_inputs_coalesce_renders_via_schedule_render_bd_3c01a1
      -> 1 passed, 0 failed
    cargo test -p caco-web --lib --tests
      -> 458 passed, 11 failed (net +1 pass; same 11 pre-existing
         failures on main).
- Whitespace: git diff --check origin/main..HEAD -> clean.

New test asserts:
- scheduleRender helper defined in app.js + exposed on window.
- Helper uses requestAnimationFrame + cancelAnimationFrame pair
  (rAF coalescing, not setTimeout debounce).
- Each of 7 input sites uses the wrapped scheduleRender(...) form.
- Bare unwrapped renderXxx()/filterXxx() forms are absent (so a
  future copy-paste regression that re-introduces a bare call
  fails the test).
